# Project Conventions & Coding Standards

This document establishes the naming, coding, and structural conventions of the repository.

## 🐍 Python Style Guide
- **Code Style:** Strict adherence to PEP-8. All code should be formatted using `black` and linted with `ruff`/`flake8`.
- **Type Hints:** Every function must have explicit type hints for arguments and return values.
  - *Example:*
    ```python
    def calculate_gini(y_true: np.ndarray, y_pred: np.ndarray) -> float:
        ...
    ```

## 🏷️ Nomenclature
- **File Names:** Lowercase, snake_case (e.g., `model_inference.py`, `load_to_bigquery.py`).
- **Function/Method Names:** Lowercase, snake_case (e.g., `predict_default_probability()`).
- **Class Names:** PascalCase (e.g., `CreditDecisionEngine`).
- **Constants:** Uppercase with underscores (e.g., `MAX_LATENCY_MS = 100`).
- **Specs Directories:** `specs/<feature_name>/` named strictly after the feature identifier in `feature_list.json`.

## 🛡️ Error Handling & Defensiveness
- **No Silent Failures:** Never catch generic exceptions without logging.
  - *Bad:*
    ```python
    try:
        score = model.predict(data)
    except Exception:
        pass
    ```
  - *Good:*
    ```python
    try:
        score = model.predict(data)
    except ModelInferenceError as e:
        logger.error(f"Inference failed: {e}")
        score = DEFAULT_COHORT_MEDIAN_SCORE
    ```
- **Fallback values:** In high-latency/scoring failure situations, fallback scores or credit limits must be pre-authorized and safe.
- **SQL Safety:** All SQL statements generated by agents or tools must be validated against writing keywords (`INSERT`, `UPDATE`, `DELETE`, `DROP`). Only read-only queries are permitted for diagnostic tools.
